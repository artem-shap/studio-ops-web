## 2. What this product is, and where the boundary sits

StudioOps is an intake and project-tracking system for a small design studio.

This repository is the **thin client layer**:
- the public site with the inquiry form,
- the client portal at `/portal/[token]`.

Data and business logic live in `studio-ops-api` (Laravel 13). There is **no** database here, no ORM, no business rules. If something needs to be calculated or persisted, that is a signal the logic belongs in Laravel.

**The BFF pattern is mandatory.** The browser talks only to the Next.js server. The Next.js server talks to Laravel with an `X-Studio-Key` header.

```
browser -> Server Action / route handler -> Laravel API
```

Never `fetch` the Laravel API from a client component. Consequences of this rule:
- CORS is not needed anywhere, here or there;
- `STUDIO_API_KEY` and `STUDIO_API_URL` are server-side variables **without** a `NEXT_PUBLIC_` prefix;
- the portal token never appears in a browser network request.

If you see `NEXT_PUBLIC_STUDIO_API_*` anywhere in the codebase, that is a defect — fix it.

## 3. The API may be asleep — handle it

`studio-ops-api` runs on a free tier that sleeps after 15 minutes of inactivity. The first request after idle takes roughly a minute to return.

Every server-side call to Laravel therefore:
- uses a generous timeout, around 60 seconds, via `AbortSignal.timeout()`
- retries once on timeout or a 502/503 response
- falls back to a designed error state with human wording, never a stack trace or an upstream status code

The landing page renders statically, so a sleeping API never blocks a first impression. The portal is dynamic by necessity and shows a loading state while the API wakes.

This is a stated trade-off of zero-cost hosting, not a bug to hide. The README says so plainly.

## 5. Conventions

**Server Components by default.** `"use client"` only where there is real state, an event handler, or a browser API. If you add `"use client"`, you must be able to name the reason. An unnecessary client component is the most common generated mistake in this codebase, and it gets recorded in `AI-NOTES.md`.

**Forms use Server Actions**, not hand-written fetch handlers.

**One Zod schema per form, shared between client and server.** Schemas live in `lib/schemas/` and are imported by both the form and the Server Action. Two schemas for one form is a defect, because they will drift.

Maximum lengths in these schemas match the Form Request rules in `studio-ops-api`. A mismatch is a defect: the user would pass client validation and then fail on the server.

**Data fetching is separated from UI.** All calls to Laravel live in `lib/api/`. Components receive data as props and only render it. No `fetch` inside a file that returns JSX.

**Errors do not leak.** A Laravel failure is logged server-side; the user sees human wording. No stack traces and no upstream error codes in the interface.

## 6. Caching — where this breaks quietly

The portal shows live project status. A cached portal page does not fail loudly — it shows a client last week's status, and nobody notices until the call.

**This project uses the previous caching model.** `cacheComponents` is not enabled in `next.config.ts`, so route segment config still applies. Before changing anything about caching, read `node_modules/next/dist/docs/01-app/02-guides/caching-without-cache-components.md`.

So `app/portal/[token]/page.tsx` declares:

```ts
export const dynamic = 'force-dynamic'
```

and passes `{ cache: 'no-store' }` explicitly, even though `fetch` has been uncached by default since Next.js 15. The route-level cache is a separate mechanism, and being explicit here is cheaper than investigating a stale-data report later.

**If `cacheComponents: true` is ever enabled, this section is invalid.** In Next.js 16 that flag removes `dynamic`, `revalidate` and `fetchCache` entirely, inverts the default so nothing is cached unless it opts in, and replaces them with the `use cache` directive plus `cacheLife`. Migrating means: delete `export const dynamic` from the portal, and add `use cache` with a `cacheLife` profile to the landing page instead. Do not mix the two models.

The landing page is the opposite of the portal: static, cached aggressively.

## 7. Security

- `STUDIO_API_KEY` and `STUDIO_API_URL` are server-side, without `NEXT_PUBLIC_`, and Zod-validated in `lib/env.ts` at startup
- The inquiry form is rate limited by IP inside the Server Action, and carries a CSS-hidden honeypot field
- Maximum lengths in Zod match the Laravel Form Request exactly. A mismatch is a defect
- The portal page sets `robots: { index: false, follow: false }` in its metadata and `Referrer-Policy: no-referrer`
- An invalid token renders an ordinary 404 with human wording. Never distinguish invalid from expired — that distinction is information an attacker can use
- The token is never logged and never sent to analytics
- Security headers in `next.config.ts`: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, and a CSP
- Never `dangerouslySetInnerHTML` with data from the API

## 9. Tests

Vitest, at minimum one test: the inquiry Zod schema accepts valid input and rejects an empty email, an over-long message, and a filled honeypot.

Components are not unit-tested — at this size the cost outweighs the signal.

CI on every pull request: `pnpm lint`, `pnpm typecheck`, `pnpm test`.

- Small, meaningful commits
- Every diff is read before it is committed. Always

**When your output gets corrected, it gets written down** in `AI-NOTES.md`: what was generated, why it was corrected, how it was corrected, and the commit hash. Typical candidates here: an unnecessary `"use client"`, a fetch to Laravel from a client component, a second Zod schema instead of the shared one, a missing `force-dynamic` on the portal, a `NEXT_PUBLIC_` prefix on a server secret, and a server call with no timeout against a sleeping API.
